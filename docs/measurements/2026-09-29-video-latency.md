# Windows App 영상 지연 1차 관측 — 2026-09-29

## 결과

Windows 원본 PC의 테스트 패턴을 NanoKVM → gateway → Windows App으로 수신했다.
20개 서로 다른 프레임의 시각을 화면에서 판독했다. **관측 시점에 보이는 원본
시각의 나이는 중앙 추정 약 129ms**였다. 물리적 모니터 표시 지연이나 입력 지연은 아니다.

| 통계 | 캡처 구간 중간값 기준 추정 | 계산상 하한~상한 |
| --- | ---: | ---: |
| 표본 p50 | 128.5ms | 88.8~171.2ms |
| 표본 p95 | 160.0ms | 121.8~225.2ms |
| 표본 최대 | 180.5ms | 135.8~238.2ms |

20개 표본의 p95는 운영 전체의 p95를 대표하지 않는다. p99는 표본 최대와 같아
해석하지 않는다. 각 통계의 하한·중간값·상한은 각각의 순서통계량이며 같은 행의
단일 표본을 의미하지 않는다. 이 범위는 통계적 신뢰구간이 아니다.

## 방법과 조건

- 사용자가 원본 Windows 브라우저에서 `/1`을 열고 Start / resync 실행.
- Windows App에서 `nanokvm-gw.yangs.sh` 재접속 후 화면 갱신 확인.
- 원본 화면의 서버 기준 timestamp, FRAME, SYNC를 Computer Use 스크린샷에서 직접 판독.
- 각 스크린샷 호출을 같은 실행 안의 Date.now() 전후 값으로 감쌌다.
- 표본 수집 구간은 약 41.5초이며 짧은 묶음으로 수집했다. 균일 주기 연속 녹화가 아니다.
- 화면 표시 SYNC 불확실성은 ±3.70ms. 보정 이후 약 46.7~88.2초에 수집.
- 캡처 호출 구간 중앙값 68.5ms, 최대 216ms. 소스 stamp 반올림 오차 ±0.5ms 포함.
- 서버 clock과 Mac wall clock의 수집 후 비교 범위는 +0.38~+0.93ms.
  위 표 계산에는 별도 가산하지 않았으며 정수 ms 단위 해석에 추가 약 1ms 오차가 있다.
- 앞선 단회 NTP 확인은 ntp.yangs.sh 기준 offset 약 +2.0ms, 구간 −1.3~+5.3ms.
  NTP 결과는 영상 지연 계산에 사용하지 않았다.
- 표시 프레임 번호/시각의 진행은 이 구간에서 원본 패턴 약 21.3회/초에 해당한다.
  requestAnimationFrame 기반 30Hz 목표가 실제로 30Hz였다는 뜻이 아니며,
  원격 영상 전달 FPS도 이 표본으로 확정할 수 없다.
- 기존 gateway/agent 및 설정은 수정하지 않았다. 실제 협상된 RDP codec,
  agent bitrate와 해상도는 이번 실행에서 별도 조회하지 않았으므로 확정하지 않는다.

## 한계

계산은 캡처 API가 호출 전후 사이의 새 화면을 반환한다는 가정에 따른다.
API 내부 캐시나 실제 프레임 timestamp는 검증하지 않았다. 소스 시계의 측정 후
재보정은 수행하지 않았으므로 Windows monotonic clock의 drift는 추가 미측정 오차다.
따라서 이 결과는 정밀 벤치마크가 아닌 약 0.1~0.2초 규모를 확인하는 1차 관측이다.

표본 2는 캡처 시작 이후에 생성된 timestamp를 담아 계산 하한이 음수다.
166ms짜리 캡처 구간 안에서 나중에 프레임을 읽었다면 가능한 결과이며, 음의
실제 지연을 의미하지 않는다. 표본을 삭제하거나 하한을 0으로 보정하지 않았다.

이 측정은 원본 draw 시각부터 캡처된 Windows App 화면까지의 경로와 화면 갱신에
따른 age를 포함한다. 브라우저 paint 완료나 HDMI scanout 시작을 직접 측정하지 않는다.
캡처·인코딩·네트워크·gateway·클라이언트별 지연 비중은 아직 구분하지 못했다.
짧은 표본 사이에 발생한 정지나 드롭도 배제할 수 없다.
